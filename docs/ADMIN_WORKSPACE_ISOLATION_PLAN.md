# План работ: раздельные админские кабинеты

## Цель

Сделать приложение пригодным для коммерческого использования несколькими независимыми администраторами.

Каждый публично зарегистрированный администратор должен получать собственный изолированный кабинет и видеть только свои данные:

- партнёров;
- клиентов;
- задачи;
- чаты;
- финансы и транзакции;
- настройки;
- уведомления;
- файлы.

Данные одного администратора не должны отображаться, искаться или открываться другим администратором.

## Выбранная модель

Модель: **личный кабинет администратора**.

Один зарегистрированный администратор = одна отдельная рабочая область.

На первом этапе не делаем:

- командную работу нескольких админов в одной организации;
- суперадминский интерфейс;
- перенос данных между рабочими областями через UI.

## Основная идея реализации

Добавить сущность рабочей области, например `Workspace` или `AdminWorkspace`.

Каждый администратор привязывается к своей рабочей области через `workspace_id`.

Все данные, которыми управляет администратор, тоже должны быть привязаны к этой рабочей области напрямую или через партнёра.

Минимальный вариант:

- `users.workspace_id` для админов;
- `partners.workspace_id`;
- остальные сущности фильтруются через `partner_id`, если они уже принадлежат партнёру.

Если для некоторых таблиц фильтрация через партнёра неудобна или рискованна, добавить им собственный `workspace_id`.

## Backend

### Модель данных

Добавить модель `Workspace`:

- `id`;
- `owner_admin_id`;
- `name`;
- `created_at`;
- `updated_at`.

Добавить поля:

- `users.workspace_id`;
- `partners.workspace_id`.

Добавить индексы:

- `users.workspace_id`;
- `partners.workspace_id`;
- составные индексы для частых админских выборок, если потребуется.

### Миграция существующих данных

Создать Alembic-миграцию:

1. Создать таблицу `workspaces`.
2. Добавить `workspace_id` в `users` и `partners`.
3. Создать одну legacy workspace для уже существующих данных.
4. Привязать существующих админов к legacy workspace.
5. Привязать существующих партнёров к legacy workspace.
6. После заполнения данных сделать обязательными поля там, где это безопасно.

Цель миграции: не потерять текущие данные и не сломать существующий запуск.

### Регистрация администратора

Добавить публичный endpoint:

`POST /api/v1/auth/register-admin`

Поведение:

- принимает email, пароль и опциональное название кабинета;
- создаёт пользователя с ролью `admin`;
- создаёт новую workspace;
- привязывает администратора к этой workspace;
- возвращает токены и данные пользователя, чтобы после регистрации сразу открыть `/admin`.

Существующий `/api/v1/auth/register` оставить для регистрации партнёров.

### Авторизация и текущий пользователь

Расширить `UserRead`:

- добавить `workspace_id` для администратора.

Добавить backend dependency/helper:

- `get_current_admin_workspace`;
- проверяет, что пользователь admin;
- проверяет, что у него есть `workspace_id`;
- возвращает текущую workspace или её id.

Если admin не привязан к workspace, возвращать ошибку доступа.

### Изоляция admin API

Все admin endpoints должны фильтровать данные по `current_user.workspace_id`.

Обновить минимум:

- `/admin/partners`;
- `/admin/clients`;
- `/admin/dashboard`;
- `/admin/finance/transactions`;
- `/admin/chat`;
- `/admin/tasks`;
- `/admin/settings`;
- `/admin/notifications`;
- admin-доступ к файлам, если он есть через клиентов или партнёров.

Правило:

- списки возвращают только данные текущей workspace;
- detail/update/delete endpoints сначала проверяют принадлежность объекта текущей workspace;
- чужие объекты возвращают `404` или `403`;
- предпочтительно использовать `404`, чтобы не раскрывать существование чужих данных.

### Создание партнёров админом

При создании партнёра из админского кабинета:

- брать `workspace_id` текущего администратора;
- записывать его в `Partner.workspace_id`;
- не принимать `workspace_id` из frontend.

Публичная регистрация партнёра должна быть отдельно переосмыслена:

- либо партнёр регистрируется без workspace и ожидает ручного назначения;
- либо публичная регистрация партнёра отключается для коммерческой модели;
- либо партнёр регистрируется по ссылке/коду конкретного администратора.

Для первой реализации рекомендуется не менять публичную регистрацию партнёра без отдельного продуктового решения.

### Чат

Сейчас admin chat выбирает все комнаты типа `admin`.

Нужно изменить:

- список комнат администратора должен включать только комнаты партнёров его workspace;
- unread count должен считать только эти комнаты;
- чтение сообщений по `room_id` должно проверять принадлежность комнаты workspace текущего админа;
- отправка сообщения админом в чужую комнату должна быть запрещена.

### Финансы

Все финансовые выборки администратора должны ограничиваться партнёрами текущей workspace.

Обновить:

- список транзакций;
- dashboard finance stats;
- top partners;
- recent transactions;
- клиентские начисления в admin detail.

### Настройки

Разделить настройки на два уровня:

- глобальные технические настройки сервиса;
- настройки конкретного кабинета администратора.

Настройки, которые видит и меняет администратор в UI, должны храниться с `workspace_id`.

## Frontend

### Маршруты

Добавить страницу:

`/admin/register`

Назначение:

- публичная регистрация нового администратора;
- после успешной регистрации redirect на `/admin`.

Существующий `/login` оставить общим:

- admin после логина идёт в `/admin`;
- partner после логина идёт в `/dashboard`.

### Auth store и типы

Обновить тип текущего пользователя:

- добавить optional `workspace_id`.

Обновить обработку `/auth/me`, login и register-admin response.

### Admin UI

Визуально можно оставить текущие страницы без крупных изменений.

Главное изменение должно прийти с backend:

- списки партнёров будут пустыми для нового администратора;
- созданные партнёры будут видны только создавшему администратору;
- dashboard будет считать только данные текущего кабинета.

### Состояния пустого кабинета

Проверить и при необходимости улучшить пустые состояния:

- нет партнёров;
- нет клиентов;
- нет транзакций;
- нет чатов;
- нет задач.

Новый коммерческий пользователь после регистрации должен попадать в понятный пустой кабинет.

## API

### Новый endpoint

`POST /api/v1/auth/register-admin`

Request:

```json
{
  "email": "admin@example.com",
  "password": "strong-password",
  "workspace_name": "Мой кабинет"
}
```

Response:

```json
{
  "access_token": "...",
  "user": {
    "id": "...",
    "email": "admin@example.com",
    "role": "admin",
    "workspace_id": "..."
  }
}
```

### Изменённый `UserRead`

Добавить поле:

```json
{
  "workspace_id": "..."
}
```

Поле может быть `null` для партнёров.

## Тест-план

### Backend

Проверить сценарии:

- admin A регистрируется и получает workspace A;
- admin B регистрируется и получает workspace B;
- admin A создаёт партнёра;
- admin B не видит партнёра admin A;
- admin B не может открыть партнёра admin A по прямому id;
- admin A создаёт клиента;
- admin B не видит клиента admin A;
- admin B не может открыть клиента admin A по прямому id;
- dashboard admin A считает только данные workspace A;
- dashboard admin B считает только данные workspace B;
- транзакции admin A не видны admin B;
- admin chat admin A не виден admin B;
- unread count считается только внутри workspace;
- настройки admin A не меняют настройки admin B.

### Frontend

Проверить:

- регистрация администратора через `/admin/register`;
- успешный redirect в `/admin`;
- новый админ видит пустой кабинет;
- второй админ не видит данные первого;
- существующий `/login` продолжает корректно разводить роли.

### E2E

Сценарий:

1. Зарегистрировать admin A.
2. Создать партнёра и клиента.
3. Выйти.
4. Зарегистрировать admin B.
5. Убедиться, что списки пустые.
6. Попробовать открыть прямой URL партнёра или клиента admin A.
7. Убедиться, что доступ запрещён или объект не найден.

## Риски

- Если пропустить хотя бы один admin endpoint, появится утечка данных между кабинетами.
- Если оставить глобальные настройки без разделения, администраторы смогут влиять друг на друга.
- Если публичная регистрация партнёра останется без привязки к workspace, такие партнёры могут оказаться "ничьими".
- Миграция существующих данных должна быть аккуратной: все текущие данные нужно сохранить в legacy workspace.

## Критерии готовности

Работа считается завершённой, если:

- новый администратор может зарегистрироваться самостоятельно;
- каждый новый администратор получает отдельный пустой кабинет;
- данные разных администраторов не пересекаются в UI и API;
- прямой доступ к чужим объектам невозможен;
- backend-тесты подтверждают изоляцию;
- frontend/e2e-тесты покрывают основной коммерческий сценарий;
- существующие партнёрские кабинеты продолжают работать.
