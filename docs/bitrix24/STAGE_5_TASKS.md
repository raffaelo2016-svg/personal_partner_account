# Этап 5. Задачи Битрикс24

Контур: задачи из Битрикс24 в кабинет партнёра и связанные задачи из кабинета в Битрикс24.

## Как сотруднику поставить задачу партнёру

1. Создайте задачу в Битрикс24, укажите название и описание.
2. Добавьте отдельный тег **`ЛКП`**. Регистр тега не имеет значения. Этот тег означает, что содержание задачи можно показать партнёру; внутренние задачи без него не импортируются.
3. В поле связи с CRM выберите **карточку нужного партнёра** в смарт-процессе партнёров или **сделку клиента**, уже связанную с кабинетом этого партнёра. Ответственный сотрудник Битрикс24 сам по себе не определяет получателя в ЛКП.
4. При необходимости укажите крайний срок — дату и время. В кабинете срок отображается по Москве. Допускается задача без срока.
5. Сохраните задачу. В ЛКП она появится у указанного партнёра в разделе задач от ЮРИТЕХ. Открытый список задач обновляется каждые 30 секунд. Задача по карточке партнёра может не иметь связи с клиентом.

Чтобы опубликовать уже существующую задачу, добавьте тег `ЛКП` и корректную связь с CRM, затем сохраните её. События создания и изменения поддерживают первый импорт. Не связывайте одну задачу с несколькими партнёрами или клиентами разных партнёров: неоднозначная задача не публикуется.

После публикации изменяйте название, описание, приоритет и срок в Битрикс24. Перенос срока и его снятие обновляются в кабинете. Партнёр может менять статус выполнения; условия задачи и срок задаёт ЮРИТЕХ. Чтобы отозвать задачу из кабинета, снимите тег `ЛКП`. После обработки изменения она исчезнет у партнёра; новые внутренние изменения не попадут в опубликованный текст. Повторное добавление тега и корректной связи с CRM публикует ту же задачу заново, без дубля. При неоднозначной или отсутствующей связи с получателем задача также скрывается.

## Условия подключения

- Установлена и активна OAuth-интеграция Битрикс24 с доступом к задачам и CRM.
- Карточка партнёра синхронизирована со смарт-процессом, тип которого задаётся `BITRIX_SMART_PROCESS_ENTITY_TYPE_ID` (по умолчанию `1070`). Для задачи по клиенту синхронизирована его сделка.
- Подписаны события `OnTaskAdd` и `OnTaskUpdate`, обработчик интеграции доступен из Битрикс24.
- Запущены фоновые процессы Celery worker и Celery beat для повторов и сверки.
- Применена миграция таблицы задач: отдельная связь с партнёром, необязательный клиент и точный срок `due_at`.

Техническая связь с CRM передаётся в `UF_CRM_TASK`: `D_<ID сделки>` для клиента или `T42e_<ID элемента>` для партнёра типа `1070` (тип смарт-процесса записывается в шестнадцатеричном виде). Выбирать её вручную по ID сотруднику не требуется — используется поле связи с CRM в карточке задачи.

## Что синхронизируется

Новая задача кабинета ставится в надёжную очередь и создаётся в Битрикс24 после синхронизации клиента либо карточки партнёра для общей задачи. В задачу передаются:

- название и описание;
- срок;
- приоритет;
- настроенный ответственный;
- настроенные наблюдатели;
- связь со сделкой клиента или карточкой партнёра;
- внешний UUID для защиты от дублей.

Точный срок хранится в `due_at` в UTC, а совместимое поле `due_date` содержит календарную дату по Москве. У задачи без срока оба поля пустые. Некорректная дата Битрикс24 не заменяется сегодняшним числом.

Повторная доставка события не создаёт вторую задачу: сохраняется связь с ID задачи Битрикс24. Задачи, ранее созданные самим кабинетом, также не импортируются повторно.

## Ответственные

Числовые ID сотрудников не зашиты в код. Для ролей кабинета используются настройки:

- `bitrix_task_responsible_partner`;
- `bitrix_task_responsible_admin`;
- необязательный создатель — `bitrix_task_creator_id`.
- наблюдатели — `bitrix_task_auditor_ids` (ID через запятую).

Если для роли нет активного сотрудника, задача остаётся в кабинете со статусом `not_scheduled` и кодом `RESPONSIBLE_NOT_CONFIGURED`. Случайное назначение не выполняется.
После настройки ответственного такую задачу нужно повторно отправить кнопкой повтора в кабинете или запросом `POST /api/v1/tasks/{task_id}/bitrix/retry`.

Проверка конфигурации без изменений:

```bash
python -m app.integrations.bitrix24.task_setup_cli
```

Проверка выводит состояние обеих подписок и параметр `partner_task_binding`. Режим `--apply` включает возможность выбрать карточку партнёра в CRM-связях задачи, сохраняя другие настроенные связи смарт-процесса, и повторно читает конфигурацию для проверки.

Сохранение проверенных ID и подписка на создание и обновление задач:

```bash
python -m app.integrations.bitrix24.task_setup_cli --apply \
  --partner-responsible-id 54 --admin-responsible-id 54 --creator-id 1509 \
  --auditor-ids 56 55 43
```

При первой производственной выкладке незаполненные роли безопасно направляются
пользователю, который установил интеграцию. Уже настроенные роли при следующих
выкладках не перезаписываются. Одновременно обеспечивается подписка на
`OnTaskAdd` и `OnTaskUpdate`:

```bash
python -m app.integrations.bitrix24.task_setup_cli --apply \
  --fill-missing-with-installer
```

## Обновления задачи

Статус задачи можно менять из кабинета: переходы «Ожидает», «В работе» и «Выполнено» сначала применяются к связанной задаче Битрикс24, а затем сохраняются в кабинете. Событие `OnTaskUpdate` содержит только ID задачи, поэтому кабинет запрашивает актуальную карточку через REST и обновляет название, описание, статус, приоритет и срок. Для опубликованной задачи партнёру получатель определяется связью с CRM, а не внутренним ответственным сотрудником Битрикс24.

Для статуса применяется безопасное соответствие:

| Битрикс24 | Кабинет |
|---|---|
| ожидает выполнения | `pending` |
| выполняется | `in_progress` |
| ожидает контроля | `in_progress` |
| завершена | `completed` |
| отложена | `pending` |

Необработанное событие хранит только технический ID задачи и повторяется фоновым процессом. Общий процесс восстановления каждые пять минут проверяет ограниченную пачку существующих связей; для импортированных задач он проверяет и снятие тега, даже если событие отзыва было пропущено. Отдельный процесс каждую минуту ищет опубликованные задачи с тегом `ЛКП`, для которых событие создания или изменения было пропущено. При первом запуске он читает отмеченные задачи; далее использует сохранённую дату изменений с перекрытием пяти минут и постраничное чтение. Это фоновое восстановление не означает, что все изменения гарантированно станут видны ровно через минуту: скорость зависит от очереди и доступности API. Тело события, комментарии и персональные данные в журнале событий не сохраняются.

## Границы функциональности

- изменение статуса из кабинета требует доступности Битрикс24; при ошибке статус в кабинете не меняется;
- партнёр не редактирует название, описание, приоритет, срок или получателя задачи, опубликованной из Битрикс24;
- удаление локальной задачи не удаляет задачу Битрикс24;
- комментарии и файлы будут подключаться на следующих этапах.

## Проверка после подключения

На тестовом партнёре создайте общую задачу с тегом `ЛКП` и сроком, проверьте её появление только в нужном кабинете. Повторите для сделки клиента. Перенесите срок, затем снимите его; проверьте дату и время по Москве и отсутствие просрочки у задачи без срока. Измените статус в кабинете и проверьте его в Битрикс24. Сохраните задачу повторно и убедитесь, что дубль не появился. Снимите тег — задача должна исчезнуть у партнёра; добавьте его обратно — должна появиться одна обновлённая задача. Внутренняя задача без тега и задача с противоречащими друг другу связями с партнёрами не должны появляться в ЛКП.

Штатная производственная выкладка запускает миграции, обновляет backend/worker/beat и выполняет `task_setup_cli --apply --fill-missing-with-installer`. Успешная локальная проверка кода сама по себе не подтверждает выкладку или подписку событий на действующем портале.
