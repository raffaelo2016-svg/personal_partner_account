# Прод-запуск и поддержка: админы, агенты, доступы

Документ для команды: что настроить перед запуском, как провести миграцию и что делать поддержке.
Версия от 6 ноября 2026 г.

## 1. Что готово

- Персональные учётные записи администраторов: супер-админ, приглашения, вход по почте или логину, блокировка, журнал.
- Агентский кабинет: регистрация агента, реферальная ссылка, закрепление партнёров, начисления, выплаты, реквизиты, материалы, поддержка.
- Корректировка начислений с причиной и записью в журнале.
- Партнёрский контур не менялся, вход существующих партнёров проверен.

## 2. Почта для приглашений и сброса пароля

Приглашения и сброс пароля отправляются письмом. Поддерживаются два транспорта, порядок выбора:

1. **Resend** — если заданы `RESEND_API_KEY` и `RESEND_FROM_EMAIL`.
2. **SMTP** — если задан `SMTP_HOST` и `SMTP_FROM_EMAIL` или `SMTP_USERNAME`.

### Вариант А. Яндекс 360 (рекомендуется для домена uritech.ru)

| Переменная | Значение |
|---|---|
| `SMTP_HOST` | `smtp.yandex.ru` |
| `SMTP_PORT` | `465` |
| `SMTP_USE_SSL` | `true` |
| `SMTP_USE_STARTTLS` | `false` |
| `SMTP_USERNAME` | полный адрес ящика, например `noreply@uritech.ru` |
| `SMTP_PASSWORD` | пароль приложения из Яндекс ID (не обычный пароль) |
| `SMTP_FROM_EMAIL` | тот же адрес, что `SMTP_USERNAME` |

В Яндекс 360 нужно включить доступ по IMAP/SMTP и создать пароль приложения для ящика-отправителя.
Пароль приложения хранится только в серверном `.env`, в git не попадает.

### Вариант Б. Resend

| Переменная | Значение |
|---|---|
| `RESEND_API_KEY` | ключ из панели Resend |
| `RESEND_FROM_EMAIL` | подтверждённый адрес отправителя на домене |

### Проверка

```bash
cd backend
python -m app.scripts.check_email                 # покажет, что настроено
python -m app.scripts.check_email --to вы@uritech.ru   # отправит тестовое письмо
```

Письмо должно прийти в течение минуты; если нет — проверьте «Спам», логин, пароль приложения и порт 465/587.

## 3. Миграция с общей учётной записи

Скрипт: `python -m app.scripts.migrate_shared_account`.

Что делает:

1. находит общую учётную запись администратора (по `--email` или автоматически);
2. создаёт приглашения на указанные почты;
3. отключает общую учётку и помечает её как устаревшую;
4. пишет событие в журнал.

### Репетиция (выполнена 6 ноября 2026)

Копия демо-базы `juritech_rehearsal`, миграция с `legacy@uritech.ru` и двумя приглашениями:

| Показатель | До | После |
|---|---|---|
| Пользователи | 7 | 7 |
| Партнёры (активные) | 1 | 1 |
| Клиенты | 1 | 1 |
| Агенты | 2 | 2 |
| Приглашения | 7 | 9 |
| Активные супер-админы | 1 | 1 |

Дополнительно проверено:

- общая учётка: `is_active=false`, `is_legacy_shared=true`, вход заблокирован;
- партнёр `ref.partner@uritech.ru` после миграции входит как обычно (роль `partner`);
- данные партнёров и клиентов не изменились.

### Порядок на боевой базе

1. Сделать резервную копию базы.
2. Прогнать `--dry-run` и сверить список приглашений.
3. Уведомить сотрудников за 5 рабочих дней (по ТЗ), согласовать дату.
4. Запустить без `--dry-run`:

```bash
DATABASE_URL="postgresql+asyncpg://..." \
  python -m app.scripts.migrate_shared_account \
  --email old-shared@uritech.ru \
  --invite admin1@uritech.ru admin2@uritech.ru
```

5. Проверить: общая учётка не входит, приглашения пришли, супер-админ входит, партнёры входят.
6. Откат: вернуть общей учётке `is_active=true`, флаг `is_legacy_shared` можно оставить.

Важно: общую учётку не удаляем — она остаётся в истории и журнале.

## 4. CI и тесты

Workflow: `.github/workflows/ci.yml` — линтер, тесты backend с PostgreSQL и Redis, OpenAPI, сборка frontend.

Что проверяется по нашей доработке в общем наборе:

- `tests/api_integration/test_admin_access.py` — доступы админов и приглашения;
- `tests/api_integration/test_login_guard.py` — капча и блокировка входов;
- `tests/api_integration/test_agent_cabinet.py` — агенты, начисления, выплаты, уведомления, корректировки;
- партнёрские наборы — регресс входа и кабинета.

Локально полный прогон может зависать из-за сбоев файловой системы на рабочей машине; для приёмки использовать CI.

## 6. Инструкция поддержки

### Вход и роли

- **Партнёр** — входит по почте и паролю, видит только свой кабинет.
- **Агент** — входит по почте и паролю, видит своих партнёров, начисления и выплаты.
- **Администратор** — рабочие разделы: партнёры, клиенты, агенты, деньги, чат.
- **Супер-администратор** — то же плюс «Админы и доступы» и журнал.

Пароли не видны никому. Забыл пароль — «Забыли пароль?» на странице входа.

### Пригласить администратора

1. «Админы и доступы» → «Пригласить админа».
2. Почта, роль, срок ссылки.
3. Скопировать ссылку из окна или перевыпустить позже.
4. Сотрудник открывает ссылку, задаёт логин и пароль.

Ссылка одноразовая и привязана к почте. Если письмо не дошло — передайте ссылку лично.

### Пригласить агента

То же окно, роль «Агент». Дополнительно агент может зарегистрироваться сам по кнопке «Стать агентом».

### Заблокировать сотрудника

«Админы и доступы» → в строке сотрудника кнопка блокировки. Доступ пропадает сразу, сессии перестают работать. Последнего супер-админа заблокировать нельзя.

### Агенты и партнёры

- В карточке партнёра блок «Агент»: закрепить, перепривязать или отвязать. Причина обязательна, всё попадает в журнал.
- Закрепление обычно происходит автоматически при регистрации партнёра по ссылке агента.
- Если партнёр зарегистрировался без ссылки — закрепите вручную.

### Начисления

- 1 000 ₽ начисляется автоматически, когда клиент партнёра переходит в статус «введение в процедуру».
- Одно дело — одно начисление.
- Отменить или вернуть начисление: карточка агента → «Начисления» → «Отменить»/«Вернуть», причина обязательна.
- После отмены сумма исчезает из «Доступно к выплате», причина видна агенту.

### Выплаты

1. Агент заполняет реквизиты.
2. Админ проверяет: карточка агента → «Принять реквизиты» (или «Нужны правки»).
3. Агент отправляет заявку.
4. Админ ведёт заявку: «Проверяю» → «В выплату» → «Выплачено».
5. Агент получает уведомление на каждом шаге.

Цикл: заявка до 14-го числа → выплата 15-го, позже — следующий месяц. Одна активная заявка на агента.

### Журнал

«Админы и доступы» → «Журнал доступа». Режимы: «Все», «Доступы», «Агенты и деньги». Видно кто, что, когда и с какого IP.

### Частые ситуации

| Ситуация | Что делать |
|---|---|
| Письмо с приглашением не пришло | Проверить «Спам», перевыпустить ссылку и передать лично |
| «Ссылка уже использована» | Войти по паролю или выпустить новое приглашение |
| «Срок действия ссылки истёк» | Перевыпустить приглашение |
| Партнёр закрепился не за тем агентом | Карточка партнёра → «Агент» → перепривязать с причиной |
| Нет начисления | Проверить статус клиента: начисление только после введения в процедуру |
| «Нет суммы к выплате» | Все начисления отменены или уже в активной заявке |
| «Сначала подтвердите реквизиты» | Проверить реквизиты в карточке агента |
| Сотрудник уволился | Заблокировать в «Админах»; при необходимости снять роль |

## 7. Ограничения текущей версии

- Двухфакторный вход не входит (по ТЗ — позже).
- Частичных выплат нет: заявка на всю доступную сумму.
- Материалы агента статичные, управление из админки не сделано.
- Уведомления только в кабинете, письма по начислениям не отправляются.
